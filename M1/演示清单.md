## M1-1 三节点链路（3 分钟）

四个终端，都在 `~/.../M1/M1-1`（或 `/mnt/c/Users/admin/Desktop/usky/M1/M1-1`）里，先 source。

```bash
# 终端1
ros2 run smartcar_m1 node_a_sensor
# 终端2
ros2 run smartcar_m1 node_b_filter
# 终端3：注意必须带 serve_alarm:=false，服务端单独起，否则第5步永远不超时
ros2 run smartcar_m1 node_c_alarm --ros-args -p serve_alarm:=false
# 终端4
ros2 run smartcar_m1 alarm_server
```

**第2步 接口契约**

```bash
ros2 interface show sensor_interfaces/msg/SensorData
```

实测输出（字段顺序就是 `distance / unit / stamp / status`）：

```
float32 distance              # 距离（米）
string unit                   # 距离单位，固定 "m"
builtin_interfaces/Time stamp # 消息生成时间
	int32 sec
	uint32 nanosec
uint8 status                  # 0=正常 1=超出量程 2=传感器错误
```

一句话讲："四个字段是我自己定的 `SensorData.msg`，顺序和类型都不能改，`status` 是给下游做有效性判断用的。"

**第3步 频率**

```bash
ros2 topic hz /processed_distance
```

实测 `average rate: 10.001`，`min: 0.099s max: 0.101s`。约 10 Hz，符合。

**第4步 动态改参**

```bash
ros2 param set /node_b_filter alpha 0.9
```

实测 `Set parameter successful`，节点 B 打印立刻变成 `alpha=0.90`：

```
[INFO] [node_b_filter]: raw=0.506  filtered=0.502  alpha=0.90  (有效 100 / 丢弃 1)
```

肉眼对比：alpha 0.3 时数值平滑、滞后；0.9 时几乎跟着原始值跳。讲一句："α 越大越信新值、响应快但抖；越小越平滑、滞后大。改参数走的是 `ParameterDescriptor` + 回调，运行中生效，不用重启。"

**第5步 报警：正常一次 + 超时一次**

```bash
# 服务端还在，发低距离，应出现 ALARM-OK
ros2 topic pub -r 10 --times 12 /processed_distance std_msgs/msg/Float32 "{data: 0.20}"
# 实测： [ALARM-OK] 服务端响应：alarm handled, distance=0.200（累计成功 3 次）

# 停掉终端4（alarm_server）后再发一次，等 1 秒
ros2 topic pub -r 10 --times 30 /processed_distance std_msgs/msg/Float32 "{data: 0.20}"
# 实测： [WARN] 报警服务超时（已等待 1.05s，阈值 1.00s，累计超时 2 次）
```

讲一句："调用用的是 `call_async` 非阻塞 + 0.1 s 独立看门狗计时，服务端没了就按 1 s 判超时，不阻塞订阅回调，所以 B 那边的滤波不会被拖慢。"

**第6步 准备一条 status=1 的消息**

```bash
ros2 topic pub --once /sensor_data sensor_interfaces/msg/SensorData \
  "{distance: 0.25, unit: 'm', stamp: {sec: 0, nanosec: 0}, status: 1}"
```

实测节点 B 立刻打印：

```
[WARN] [node_b_filter]: [DROP] 丢弃无效数据 status=1(超出量程) distance=0.250
```

要能解释："status=1 表示这帧超出量程、`distance` 不可信。滤波是递推的，脏值一旦进了历史，后面几十帧都会被它污染，所以我直接丢掉并计数，不进滤波器。`0=正常 / 1=超出量程 / 2=传感器错误`。"

## M1-2 Launch 编排（4 分钟）

按指南是"一条 launch 起 robot1，再起 robot2"，所以开两个终端各跑一条（两个终端都在 `M1/M1-2`）：

```bash
# 终端1：只起 robot1 三个节点
ros2 launch smartcar_m1_ns bringup.launch.py \
  namespace:=robot1 second_namespace:= \
  params_file:=$PWD/src/smartcar_m1_ns/params/params_robot1.yaml

# 终端2：同一个 launch 再起 robot2
ros2 launch smartcar_m1_ns bringup.launch.py \
  namespace:=robot2 second_namespace:= \
  params_file:=$PWD/src/smartcar_m1_ns/params/params_robot2.yaml
```

（`second_namespace:=` 留空就是"只起一组"；这是 launch 里显式支持的入口。如果考官想看"一条命令起两组"，再加一句 `params_file2:=.../params_robot2.yaml` 即可，两种都行。**这是我们和详细 README 的差异点之一**：详细版要求一条命令起两组，展示指南改成两条同样的 launch。）

**第3步 让考官查阈值**（实测）

```bash
ros2 param get /robot1/node_c_alarm alarm_threshold   # Double value is: 0.3
ros2 param get /robot2/node_c_alarm alarm_threshold   # Double value is: 0.5
```

**第4步 话题隔离**

```bash
ros2 topic list | grep processed_distance
# /robot1/processed_distance
# /robot2/processed_distance
```

**第5步 不存在的参数文件**（先 Ctrl+C 停掉一组，腾出名字）

```bash
ros2 launch smartcar_m1_ns bringup.launch.py params_file:=/tmp/does_not_exist.yaml
```

会打印人话报错并主动退出，不吐 Python Traceback（`grep Traceback` = 0 行）：说明是 `OpaqueFunction` 里先校验文件、失败打 `LogInfo` + `EmitEvent(Shutdown)`，不是让节点各自崩。

**第6步 改一组 alpha，看另一组**

```bash
ros2 param set /robot1/node_b_filter alpha 0.9
ros2 param get /robot1/node_b_filter alpha   # 0.9
ros2 param get /robot2/node_b_filter alpha   # 0.6  ← 没被带偏
```

讲一句："两组是不同进程、不同命名空间、各自一份 YAML，参数不共享；`ros2 param set` 只作用于指定全名节点。"

## M1-3 时间与坐标（5 分钟）

**第1步 播 bag（带 --clock）+ 起投影节点**（两个终端，在 `M1/M1-3`）

```bash
# 终端1：TF + 投影
ros2 launch m1_three m1_three.launch.py use_sim_time:=true extrinsics_file:=extrinsics.yaml
# 终端2：回放
ros2 bag play ~/m13_bag --clock --rate 2.0
```

注意：bag 要放在 WSL 的 `~/` 下，**不能放 `/mnt/c`**（9p 文件协议下 sqlite 小随机读极慢，`ros2 topic hz /scan` 会 9 秒零条）。这条已经写进 README 第九节。

**第2步 证明 TF 链通**（实测）

```bash
ros2 run tf2_ros tf2_echo camera_link laser_link
# At time 0.0
# - Translation: [0.050, 0.000, -0.100]
# - Rotation: in Quaternion (xyzw) [0.000, 0.000, 0.000, 1.000]
```

数值对得上：雷达在 (0.15, 0, 0.20)、相机在 (0.10, 0, 0.30)，两者差 (0.05, 0, −0.10)。讲一句："`camera_link` 到 `laser_link` 不是直连，走 `map → odom → base_link → {laser_link, camera_link}` 这条静态链，tf2 会自己串起来。"

**第3步 展示投影图**

```bash
ls projection_*.png    # 至少 3 张
```

已有 4 张：`projection_01_t0.612.png`、`projection_02_t2.204.png`、`projection_03_t3.834.png`、`projection_04_nondefault_laserz0.45.png`。

**第4步 换第二套外参重跑**

```bash
# 重建一套非默认外参的 bag（雷达抬高到 0.45、相机 0.75、fx 改 420）
python3 make_bag.py --frames 40 --laser-z 0.45 --camera-z 0.75 --fx 420 \
   --out ~/m13_bag_alt --extrinsics extrinsics_alt.yaml
# 再跑投影（extrinsics_file 指到 extrinsics_alt.yaml），生成 projection_04_nondefault_laserz0.45.png
```

对比肉眼可见：点整体下移（v 从约 248 移到约 261）、横向收窄。讲一句："外参一变，投影位置就跟着变，说明投影是真的用 TF + 外参算的，不是写死像素。"

**第5步 指一个投影点说出它的激光距离**（这条最容易卡，公式记住）

默认外参下，相机比雷达高 0.10 m（0.30 vs 0.20），所以像平面纵坐标：

\[
v = \frac{500 \times 0.1}{r + 0.05} + 240 \quad\Rightarrow\quad r = \frac{50}{v - 240} - 0.05
\]

| 画面位置 v | 反解距离 r | 说明 |
| :-- | :-- | :-- |
| 248 | ≈ 6.0 m | 中间偏上那一排蓝点（远处墙 `r = 6.0 + 0.15 sin(...)`） |
| 252 | ≈ 3.9 m | 蓝绿过渡 |
| 264 | ≈ 2.0 m | 偏黄 |
| 270 | ≈ 1.6 m | 两侧红色点（侧向障碍物 `r = 1.6`） |

现场话术："这个点在我图上偏蓝、v 大概 248，按当前外参反解就是正前方约 6 m 的那面墙；靠下的红点是我场景里 1.6 m 的侧向障碍。颜色也是按距离上色的，近红远蓝。"

（若换 `extrinsics_alt.yaml`，高差变 0.30、fy 仍 500，公式换成 \(v = 150/(r+0.05) + 240\)，同 v 对应距离大约是原来的 1/3，别套错。）

## M1-4 调优与故障记录（7 分钟）

**第1步 起优化版，报四个数**（两个终端，在 `M1/M1-4`）

```bash
# 终端1
python3 camera_pub.py
# 终端2
python3 image_proc.py
# 终端3
python3 measure_delay.py --seconds 15
```

实测四个数：输入 **29.99 Hz**、输出 **29.5–30.0 Hz**、控制 **20.0 Hz**、端到端 **P50 9.5 ms / P95 20.8 ms**（基线是 24–26.7 Hz / 4.5 Hz / 4.47 Hz / P95 1351 ms）。自查表要求 30/30/20，对得上。

**第2步 只换掉一端，指瓶颈**（三个组合，各跑 10 s 看 `ros2 topic hz`）

```bash
# A 只换发布端（旧发布 + 新处理）
python3 baseline_camera_pub.py & python3 image_proc.py
#   实测输出 4.4 Hz → 瓶颈在发布端

# B 只换处理端（新发布 + 旧处理）
python3 camera_pub.py & python3 baseline_image_proc.py
#   实测输出 25.7 Hz → 处理端还有上限但已不是主瓶颈

# C 两端都换
python3 camera_pub.py & python3 image_proc.py
#   实测 30 Hz → 两头都解开才到线
```

话术："只换一端都到不了 30，说明是**两个瓶颈串联**，不是单点；所以我把发布端（逐像素双重循环造帧、1280×720 放大再缩小、bgr8 三通道）和消费端（depth=30 排队、单线程执行器）一起改。"

**第3步 打开 FAULTS.md 讲一条**（推荐第①条，证据最硬）

探针死锁：`measure_delay.py` 在回调里调 `rclpy.shutdown()`，同时无时间上界 → 进程挂住不退出。`ps -o pid,etimes,pcpu` 显示 `etimes=283, pcpu=0.0`，SIGTERM 不响应。修复：改主线程 `spin_once` 轮询 + `timeout --kill-after`；验证：无发布者时 4 秒退出、`exit=2`。其余四条：depth=30 的排队指纹（P50 1333 / max 1353，方差极小）、单线程执行器饿死控制（控制频率=输出频率）、Python 逐像素 + 放大回路、以及"只改一端就够"被交叉实验否掉。
